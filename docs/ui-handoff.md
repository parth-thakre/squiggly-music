# Renderer guide

The renderer lives in `apps/desktop/renderer/src/app/`. It runs in three places: the desktop app, where `window.squiggly` is the preload bridge and libmpv plays audio; the browser build (`npm run web`), where the same UI talks to the host's `/api/*` bridge and plays through an audio element; and the Android app, where `window.squigglyAndroid` (`apps/android/web/bridge.ts`) runs the connector in the page and a native Media3 player plays the queue. [android.md](android.md) has the details.

## Desktop contract

Import types from `packages/core/contracts.ts`. `window.squiggly` (see `apps/desktop/preload/index.ts`):

| Method | Purpose |
| --- | --- |
| `snapshot()`, `subscribe(listener)` | Authoritative player, diagnostics, and server state |
| `player.playId` in the snapshot | A string that changes whenever a song starts from the top: another entry, the same entry again (repeat all over one song), a repeat-one loop, a jump to the entry playing. Never on a seek or pause; `''` before anything has played. The audio host sets it; the main process reports plays by it. The renderer store has the same `playId` on every platform: this one on the desktop, a new one per load in the browser, the native player's per-play counter on Android |
| `command(command)` | Play, pause, stop, previous/next, seek, volume, output device, restart |
| `command({ type: 'repeat', mode })`, `command({ type: 'shuffle', on })` | Queue modes, owned by the audio host and shown as `player.repeat` (`off`, `all`, `one`) and `player.shuffle` in the snapshot. Shuffle on reorders the songs after the current one; off leaves the queue as it is. While shuffle is on, a new queue (`playTracks`, `openFiles`) plays from the chosen song with the rest in random order; radio and a restored queue keep theirs. Repeat on stops radio, and starting radio turns repeat off. The main process saves both (`play-modes.json`) for the next launch |
| `openDropped(files, 'play' \| 'queue')` | Files dropped on the window. The renderer passes the `File` objects; the preload looks up their paths with Electron's `webUtils.getPathForFile` and sends them straight to the main process, so no path reaches the renderer, and a `File` the page made itself has none. The main process checks them as `openFiles` limits its dialog (audio extensions, regular files) and leaves out folders and anything else, counting them in `skipped`. A drop of more than 1000 files is refused whole. `queue` adds to the end when something is loaded; `play` replaces the queue. The renderer never reads the files |
| `openFiles()`, `connect(connection)`, `disconnect()` | Local files; server login, saved encrypted when the system allows (`server.saved`, `server.canRemember` in the snapshot) and reconnected at launch (`server.reconnecting`, `server.reconnectError`). Settings › Disconnect calls `disconnect()`, which stops playback, forgets the saved sign-in, and returns to the connect screen |
| `playTracks(trackIds, startIndex)` | Replace the queue with up to 500 library tracks the main process has returned |
| `queue.add(ids, 'next' \| 'end' \| index)`, `queue.move`, `queue.remove`, `queue.clear` | Edit the queue (up to 1000). An index inserts before that entry (a drop onto the queue). The playing song cannot be removed. Indexes refer to the latest snapshot |
| `queue.jump(index, entryId)` | Play a queue entry. The entry id makes the jump land on that exact entry, even when the same song appears twice |
| `radio.start(seed)`, `radio.stop()` | Radio from a song, album, or artist. The main process owns it and keeps topping up the queue while every window is hidden |
| `resumeQueue()` | Load the server-saved queue paused at its song and position |
| `library.*` | `LibraryApi`: browse, search, star, rate (`rate(kind, id, 0 to 5)`, where 0 clears; items carry `userRating` when rated), playlists and editing, radio (`similarSongs`, `topSongs`), `lyrics`, what other accounts are playing (`nowPlaying`) |
| `library.tracks(sort, offset, size, seed)` | Every track on the server, up to 500 at a time, sorted as Records sorts (Newest, A to Z, By artist, Most played, Recently played, Random, Top rated; `seed` keeps a random order across pages). A page shorter than `size` is the last. Navidrome's own API does the sorting: the connector signs in to it with the account's password (`POST /auth/login`), keeps the session token in memory, takes the fresh one each answer brings, and signs in again when it's refused. Other servers, or a Navidrome whose own API is out of reach, answer in the server's one order (`search3` with an empty query) with `sorted: false`, and the Tracks page hides its sorts. The page asks for 200 at a time as it scrolls |
| `library.coverUrl(coverArt, size)` | `squiggly-art://` URL; the main process fetches art, credentials never reach the renderer |
| `library.artistInfo(artistId)` | `getArtistInfo2`: the biography as plain text (the server's HTML stripped, its Last.fm link dropped), links, and similar artists that are in the library. Every field may be empty, and the artist page then shows nothing. Image addresses are external, so the renderer doesn't load them |
| `library.createShare(ids, description?, expiresAt?)`, `library.shares()`, `library.deleteShare(id)` | Public links (Subsonic shares) to songs, one record, or one playlist. `expiresAt` is epoch milliseconds; without it the server picks (Navidrome: a year). Each `Share` has its public `url`, `description`, `created`, `expires`, `visitCount`, and `entries`. Navidrome answers only with `EnableSharing` on; otherwise the calls fail with a plain message, and Settings › Shares stays hidden. The menus' Share… opens the dialog in `share.tsx`. On phones it's a sheet with its own history entry, so Back closes it, and it closes when the session ends |
| `library.songsByGenre(genre, offset, size)` | One genre's songs, up to 500 at a time (`getSongsByGenre`). The genre page asks for 200 at a time as it scrolls |
| `library.nowPlaying()` | What other accounts on the server are playing (`getNowPlaying`), as `{ username, track }`. The connector leaves out this account's own players and a song someone has on two players at once. Home reads it once per visit and hides it when it's empty or fails |
| `library.radioStations()` | The server's internet radio stations (`getInternetRadioStations`): `{ id, name, homePageUrl }`, the home page http(s) only or null. Read-only. Stream addresses stay with the connector, as song streams do: the main process, the browser build's host, the Android bridge. Stations whose stream isn't http(s), or whose id is over 248 characters, are left out |
| Stations in the queue | `stationTrack(station)` (`packages/core/stations.ts`) makes a `Track` with `source: 'station'`, the station's id marked as a station's (`station:` in front, so a server that numbers songs and stations alike can't have one taken for the other; `stationIdOf(track)` gives the server's id back), its name as the title, and no artist, album, duration, or cover. `playTracks([track.id], 0)` and `queue.add` take it like a song once `radioStations()` has listed it; the main process looks up its stream and the audio host loads it. Seeks on a station do nothing, repeat one is off while one plays, and it is never reported, saved in the server's queue, or used to seed radio |
| `player.stationTitle` in the snapshot | What the playing station announces (ICY StreamTitle), from mpv's `metadata/by-key/icy-title`. Null when it announces nothing, and for anything but a station. The Android bridge reports the same from ExoPlayer (`AndroidPlayback.stationTitle`); the browser can't read it |
| `library.albums('byYear', offset, size, { fromYear, toYear })` | Records from those years, oldest first. Only `byYear` takes years. Records' decade filter uses it; the decades offered are the ones the automatic playlists find |
| `library.search(query, options?)` | `search3`. Left out, the options mean 8 artists, 16 records, and 40 songs; `artistCount`, `albumCount`, `songCount` (0 to 200, 0 skips the kind) and `artistOffset`, `albumOffset`, `songOffset` (0 to 1,000,000) page each kind. `capped` says which kinds came back full: there may be more, and the Search page offers See all. Subsonic gives no totals. The page's tab (`{ view: 'search', query, type?: 'artists' \| 'albums' \| 'songs' }`) pages one kind, songs 100 at a time |
| `settings()`, `updateSettings(changes)` | Stored preferences; re-read `settings()` after a failed update |
| `extensions.list()`, `subscribe`, `setEnabled`, `reload`, `remove`, `openDir`, `writeClipboard` | Extensions in `<config>/extensions`. `remove` moves the folder to the trash. The runtime in `extensions/` is the only caller |
| `config.dir`, `config.read()`, `config.subscribe(listener)`, `config.openDir()` | The config folder: `keybindings.json` and `themes/*.json` as parsed JSON, with plain errors for files that couldn't be read. Pushed again whenever their contents change |
| `window.toggleMini()`, `window.setAlwaysOnTop(on)`, `window.isMini` | The mini player window |
| `window.followWhileHidden(on)` | A hidden window gets no snapshots until it's shown; on, it keeps getting them. The sleep timer asks for this while "after this song" waits, so it still pauses in the tray |
| `exportDiagnostics()` | Save a credential-free report |
| `saveM3u(name, entries)` | Save an extended M3U (`packages/core/m3u.ts`) through a save dialog as `<name>.m3u8`. Entries come from `m3uEntry(track)`; songs from the server carry `path` as the server reports it, and the main process writes files from this computer with the paths it opened them from (Open files or a drop, `main/localPaths.ts`), which the renderer never sees. Songs without a path are written as `artist/album/title.suffix`, with a comment at the top saying so. No stream addresses or credentials. The browser build downloads the same file instead (`exports.ts`). Android's WebView doesn't download, so `window.squigglyAndroid.saveM3u` checks the entries with the same schema and hands the file to the system's document picker (`saveFile` in `SquigglyPlugin.kt`) |
| `kept.state()`, `kept.present()`, `kept.container(kind, id)`, `kept.subscribe(listener)` | Songs kept on this computer. `KeptState` has the containers (a record, playlist, or mix's draw: `kind`, `id`, `total`, `present`, `bytes`), the downloads (`jobs`: waiting, keeping, paused, stopped, with `done` of `total` and a plain `error`), `usedBytes` of `limitBytes`, the kept folder (`dir`), and a one-time `notice`. `present()` lists every kept track id. Pushes on `squiggly:kept` carry progress, at most every 250 ms; a new `revision` means read the state again. No song's path ever crosses; only the folder's, as `config.dir` |
| `kept.keep(request)`, `kept.cancel(kind, id)`, `kept.forget(kind, id)`, `kept.forgetAll()`, `kept.openDir()` | Keep a record, playlist, or mix's current draw (by track ids the main process has returned), stop or clear a keep, forget one, forget everything, show the folder. `keep` answers once the keep is admitted (there is room under the limit and on the disk), then the main process fetches two songs at a time whatever the page does. Keeping again fetches only what is missing, and replaces a playlist's or mix's list |
| `retryServer(passive?)` | Asks the server again while it is out of reach. `passive` (focus, the network coming back) is skipped when an answer came in the last five seconds |
| `Result.unreachable` | On a failure: no answer at all (the connection failed, the request timed out, or a gateway said 502, 503, or 504), as opposed to an answer that refused. The message is the connector's own, unchanged |
| `server.reach`, `server.queuedPlays` in the snapshot | Whether the server answers (`away`, since when, `checking`, `checkedAt`), and finished plays waiting to be reported. Absent from older hosts: online, none |
| `player.fromDevice` in the snapshot | The current entry is a kept song and mpv has its file open (not the stream). The signal-path line says "Playing the copy kept on this device." only then |
| `settings.keptLimitMb` | The room kept songs may take, 64 to 1,048,576 MB (1024 × 1024 bytes), 4,096 unless set. Lowering it removes nothing; new keeps past it are refused |
| `Track.size` | The file's size in bytes as the server reports it, when it does. Keeping uses it to check the limit before fetching |
| `updates.check()`, `updates.install()`, `updates.open()` | Updates from GitHub releases; the state is `update` in the snapshot (`mode` install, notify, or off, which is development builds and a Flatpak; `status`; `version`). `install()` restarts into a downloaded update, `open()` opens the new release's page for copies that can't update themselves |

Queue entries have identities: `snapshot.player.entryIds[i]` names the entry at `queue[i]`. Select and seek by entry, not by track id: `queue.jump` takes the entry id, and seek commands carry the `entryId` captured when the gesture began, so a seek that lands after the track changed is refused instead of seeking the wrong song.

On the desktop the main process reports plays and saves the queue; the renderer must not call `library.reportPlay` or `library.saveQueue` there. A finished play that gets no answer waits in `<userData>/plays.json` (500 at most, bound to the account) and is sent, oldest first with its own time, once the server answers. A report still on its way when the account changes, or when the queue is cleared, is dropped when it comes back.

### Offline mode

The process that talks to the server decides whether it answers, with one machine for every host (`packages/core/reach.ts`): the desktop's main process, the Android bridge, and the browser build's `previewLibrary.ts`. A call that gets no answer (`Result.unreachable`) doesn't by itself mean the server is gone, since one slow request can time out while the rest are fine. It starts one confirming probe (a ping, 8 seconds at most; ten failures at once still start one); only when that gets no answer either is the app away. An answer that refuses changes nothing: the page shows its error. While away the host answers library calls at once without contacting the server, so only a probe ends it: every 30 seconds, Retry, or a passive check when the window regains focus, becomes visible, or the network comes back (never the `offline` event: a server on this computer can answer while the network is down). A slow call that began before the outage and succeeds late doesn't end it.

While away, Home shows the Kept page (the notice where nothing can be kept), and every other page that needs the server shows "Your server is out of reach" with Retry and Open kept songs. The app never moves to another page on its own. Only kept songs play: a list plays from the chosen song if it is kept, or the next kept one, and song rows that aren't kept are dimmed and say so. Stars, ratings, radio, sharing, playlist edits, and Go to record or artist are hidden. Now playing isn't reported, finished plays wait, and the queue isn't saved (a change made meanwhile is saved once the server is back). At launch, with the saved server unreachable and songs kept for that account, the app waits four seconds and opens away; with nothing kept it shows the connect screen with the reason, as before, so a server that moved can still be changed.

### Kept songs

The desktop keeps songs in `<userData>/kept`: one file per song and cover, named `s-` or `c-` plus the first 32 hex digits of a SHA-256 of the id, and `index.json` (`packages/core/kept.ts` has its shape and bounds; `tests/fixtures/kept-index.json` shows it). The index records each song's Track as the library returned it (without stars or ratings, which go stale), each container's songs, and each cover. How many songs a container has kept, and whether a song or cover is still needed, are never stored: they follow from the containers. Two orders are never broken: a file is whole, synced, and renamed before its entry exists, and the index is written without an entry before its file is deleted. Only names the writer makes (`KEPT_FILE`) and partial files are ever deleted. A broken index is set aside as `index.broken.json` and the Kept page says so once. Bounds: 20,000 songs, 2,000 containers, 5,000 songs a keep, 16 KB of Track JSON a song, 32 MiB read and 24 MiB written for the index, at least 256 MiB left on the disk, 200 covers a keep. A keep that would pass one is refused, since the index is read whole or not at all; a record, playlist, or mix already kept can always be kept again. The two downloads count against the limit together, as each chunk arrives. A song whose headers don't come within 15 seconds, whose body stops for 30, or whose connection drops got no answer: every keep pauses, and the host starts its confirming probe. Kept songs belong to one account; another sign-in, or Disconnect, forgets them. A song queued before it was kept keeps streaming; the next queue built from it uses the kept file. LRCLIB is contacted only when both the call and the stored setting allow it.

Mutations return `{ ok: true, value }` or `{ ok: false, error }` and every failure is shown.

## Renderer conventions

- **Playlist edits** go through `playlistEditor(id)` in `library.ts`, or `usePlaylist(id)` in components. There is one editor per playlist, shared by its page and every menu. It queues edits and sends them to the server one at a time, then reconciles the local list with the server's read-back. Don't call the playlist mutations in `library.*` directly from views. New playlists go through `createPlaylist()` in `menu.tsx`, which refreshes the playlist list and opens the new one.
- **Menus and commands** register through `registry.ts`. Ids are namespaced by owner (`builtin:play`). Registering an id that is still live throws `RegistryCollision`; dispose the old registration first. Disposers are idempotent and never remove a newer registration with the same id. `registry.scope(owner)` gives an extension its own add functions and one `dispose()` for everything it added.
- `tracksOf(target)` in `menu.tsx` returns a `Result`. Show its error; don't assume the tracks loaded.
- **Navigation state** lives in the route. The Records and Tracks sorts are part of the route, so Back returns to the same order and scroll offset. So is the Records decade (`decade`). A fresh start opens Home (`{ view: 'home' }`); a reload stays where it was. Home's shelves each load on their own through `useResource`, twelve records at most, except that Your mixes waits for Most played's list to learn whether there is history. Its automatic playlists draw their songs only once their tiles scroll into view, through `mixTracks`, the same cached draw the Playlists and Mixes pages use, so a tile's sleeve matches what its play button plays.
- **Contrast.** `--accent` is for marks and large type (3:1 against the ground). `--accent-text` is for normal-weight text: it keeps 4.5:1 against both the ground and the selected-row tint. Use it for the current track number. Lyrics stay in ink and soft: the current line is ink and its words fill from soft to ink as they are sung.

## Browser build

The browser build uses `bridge/previewLibrary.ts` instead of `window.squiggly`. `npm run web` and `npm run preview` bind 127.0.0.1. Reaching them from another address requires `SQUIGGLY_WEB_PASSWORD` (12 or more characters) on the host; without it `/api` serves loopback only.

| `webSession` | Purpose |
| --- | --- |
| `status()` | `{ required, signedIn, connected, serverName, pageConnection }`: whether the host wants its password and this browser has given it; whether the host has a server for this browser, and its name; and whether that server is the page's own (`connect`) rather than the one the host was started with (`SQUIGGLY_PREVIEW_NAVIDROME_*`). Nothing about the server until signed in. An unreachable host reads as signed out |
| `signIn(password)`, `signOut()` | The HttpOnly session cookie. Signing out also makes the host forget this browser's connection |
| `connect(connection)`, `disconnect()` | The connect screen and Settings › Disconnect. `POST /api/connect` resolves the address as the desktop does (`resolveServerAddress`: HTTPS, then HTTP, for an address without a scheme), pings with the login, and keeps the connector in the host's memory under a random id in an HttpOnly, SameSite=Strict `squiggly-connection` cookie. It answers `{ serverName }` or the connector's own message. The host keeps at most 32 connections (the one idle longest goes first) and drops one after 24 hours unused; nothing is written to disk. A browser's own connection comes before the host's. Only a page connection can be disconnected, which stops playback, empties the queue, and returns to the connect screen (or to the host's own server, if it has one). On the host's own server, Settings › Connect to another server opens the connect screen over it (`player.chooseServer`); connecting empties the queue, and Back returns to the library as it was |
| `onSignedOut(listener)` | Fires when any `/api` call returns 401, so the UI can return to the sign-in screen. On a page connection, playback stops and the queue empties there and then, since a sign-out from any tab makes the host forget the connection; a queue from the host's own server waits, paused |
| `onDisconnected(listener)` | Fires when a library call returns 503 with `Not connected to a server. Connect from the page.` (the host restarted and forgot the connection, say). The page stops playback, empties the queue, and asks the host again: back to the connect screen, or to the host's own server if it has one. Stream failures check `status()` for the same reason, and treat another server in its place (the host's own, after it forgot the page's connection) as a disconnect too, so a song is never asked for from an account it didn't come from |

The browser build keeps nothing, not even its own page: there is no service worker, so the page needs its host. The host flags a library call that got no answer (`unreachable: true` in the JSON), and the page runs the same reachability machine, so it shows the notice (without Open kept songs) instead of failing page by page. A host that itself can't be reached is the sign-in flow's business, as before.

In web mode the page shows the sign-in screen until it's signed in (or the host has no password), then the connect screen (`Connect` in `App.tsx`, shared with the desktop and Android) until the host has a server for it. The password goes over the wire once, to the same-origin host; the renderer keeps nothing but the form fields. The cookies are same-origin, so `<audio>` and `<img>` URLs under `/api` need no extra headers, and the page never sees a stream address. A station plays from `/api/station?id=…`, which the host relays from the station's own address.

## Android app

`window.squigglyAndroid` (`AndroidBridge` in `packages/core/contracts.ts`) is installed by `apps/android/web/main.ts` before the renderer loads. `library.ts` takes its `library`, and the connect screen and Settings › Disconnect use its `session`, as they use the desktop's bridge. `player.ts` keeps the queue in the page (the browser's queue code), and every change to `entryIds` goes to `player.sync()`, which sends the native player only the edits (`apps/android/web/queue.ts`). Loading an entry is `player.load(entryId, …)`, never an index. The native player moves between songs by itself; its reports name the entry playing and a `playId` that changes whenever an entry starts from the top, which is a new play for reporting. Reports from before the page's last load or queue replacement are dropped by sequence number.

Covers use the browser build's `/api/cover?id=…&size=…` addresses; the native side answers them (from kept covers first), so no component sees a credential. The page reports plays and saves the queue itself, under the same settings as the browser; `library.reportPlay` goes through the bridge's queue of plays waiting for the server (`localStorage` `squiggly.plays`).

`window.squigglyAndroid.kept` is the desktop's `kept` without `openDir` and `dir`, over `Kept.kt`, which owns the index natively so the player finds kept files with the page asleep. `session.retry(passive)` is the desktop's `retryServer`, and `session.get()` carries `reach` and `queuedPlays`. `AndroidPlayback.local` says the entry playing is a kept file the player opened, and the deck says so as on the desktop.

## Audio truth rules

- Unknown remains unknown. Do not turn missing sample rates or bit depths into sensible-looking defaults.
- Distinguish source metadata, decoded sample format, mpv output, and unverified OS/DAC behavior.
- Exclusive output is a request. `exclusiveRequested` says what mpv accepted, not what the OS granted; never badge it as bit-perfect.
- `AudioPath.sink` is the Linux sound server's report about the sink mpv plays into, filled in by the main process (`main/sinks.ts`) and null when unknown. It is not what the DAC receives and never a bit-perfect claim; equal rates "match", nothing more. `sink.route` says how the sink was found: `stream` by following mpv's stream, or `device` and `default`, which are guesses. `resampling` is true only when the route is `stream` and both rates are known and differ; a guess leaves it null. The deck says something only when the server resamples. The words live in `packages/core/sinks.ts`.
- A raw stream request does not prove the server returned unmodified audio.
- Volume below 100% means attenuation. Decoder sample format is not original file bit depth.
- The desktop plays through libmpv only. The browser build plays through the browser and says so in the signal-path sentence. The Android app plays through ExoPlayer, asks for the original file as the desktop does, and says when it fell back to the server's MP3.

## Performance and security rules

- No per-frame clock in app-wide state. The squiggle interpolates between snapshots; views subscribe with selectors.
- The seek squiggle animates continuously while visible; that is intentional. It draws every frame while playing and 30 frames a second while paused, and draws nothing while the window is hidden. Reduced motion gets a still wave. Other decorative motion stops while paused or hidden.
- Lyrics run one animation frame loop while playing and visible. It writes each sung word's progress to its span (`--p`, `data-progress`) and re-renders only when the line changes; paused, it paints once. Word times come with the lyrics (`wordTiming`); lines without exact times are estimated by `timeWords()` in `packages/lyrics/words.ts`, the same on desktop and web. Reduced motion lights whole words and drops the blur.
- Window long lists and page the library. Caches are bounded.
- Never import Node, Electron, Koffi, server authentication, or the private player protocol into renderer code.
- Keep passwords out of renderer state and storage; never hand authenticated URLs to components. The browser build's connect screen sends the password to its host once and forgets it; the host keeps it in memory only. The Android app is the one exception to the first half: the page is the whole app there, so the connector holds its token in the page's memory, and the password passes through the bridge at sign-in and at launch. It is never stored in the page (`SecureAccount.kt` keeps it sealed natively) and never logged: Capacitor's logging is off because it would write plugin arguments to logcat.

`npm run check` runs typecheck and tests; `npm run test:desktop` checks the preload bridge and process isolation.
